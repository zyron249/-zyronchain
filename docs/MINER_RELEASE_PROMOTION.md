# Miner release promotion boundary

ZyronChain miner packaging and miner publication are separate security boundaries. Candidate workflows may build, checksum, attest, and smoke-test self-contained Windows/macOS/Linux artifacts while public mining remains disabled. Candidate availability alone is not authorization to publish or advertise mining as live.

Candidate checksum generation is also fail-closed at the filesystem boundary. The release manifest must recursively hash every regular file in the candidate tree except the root `SHA256SUMS` file itself, in deterministic path order. Directory traversal must not follow or silently omit symlinks, junction/reparse-style objects, FIFOs, sockets, devices, or any other non-regular entry; encountering one aborts manifest generation. npm executable shims that exist as symlinks in the development `node_modules/.bin` tree are deliberately materialized as regular files during miner packaging, but only when their canonical target remains inside the source `node_modules` tree and resolves to a regular file. Source files are descriptor-bound before destination creation: the opened source descriptor must still be a regular file with the same device/inode identity that was validated, so replacing a checked regular entry or symlink target before copy fails closed rather than following raced pathname state into the candidate. Source directories are identity-bound for traversal as well: the runtime materializer records the validated directory device/inode, revalidates that identity immediately before and after reading directory entries and around child traversal, and requires each child pathname to continue resolving inside the canonical source root. A directory replaced by a symlink or different inode therefore aborts packaging before replacement bytes can be admitted as a successful candidate. The runtime materializer must reject any destination that already exists, even if empty, so stale regular files or prior-run state cannot survive into a candidate and become part of its checksum identity. Freshness is enforced again at the creation boundary: the final destination directory is created non-recursively so a path that appears after preflight fails closed rather than being accepted, and the created directory's canonical identity and source-root separation are revalidated before any source entry is copied. The destination parent must already be a real directory; destination-side substitutions are not followed as a way to satisfy freshness. The materializer must also reject a destination that is the canonical source root or lies beneath it, before creating destination material, so packaging cannot recursively copy the runtime tree into itself and exhaust disk or produce non-deterministic checksum coverage. A symlink that escapes the source root or resolves to a non-regular object aborts packaging rather than copying host data into the candidate. The checksum walker itself remains strict and never follows a symlink in the release candidate. This closes checksum coverage over the complete distributable tree but does not replace platform signing, provenance, SBOM review, immutable-release review, or public-mining activation evidence.

`docs/miner-release-promotion.json` is the fail-closed promotion policy. The schema-v5 top-level object must contain exactly the canonical release identity fields, the established activation/publication/verification booleans plus `sbomVerified`, `assets`, `assetSha256`, and `evidence`; unknown, typo, or shadow top-level fields are rejected rather than silently ignored. While launch evidence is incomplete it must keep every canonical activation/publication/verification boolean false, exactly the `windows`, `macos`, and `linux` platform asset keys present with null values, and exactly the canonical evidence keys `windowsSigning`, `macosSigningOrNotarization`, `linuxSigning`, `provenance`, `checksums`, `windowsSbom`, `macosSbom`, `linuxSbom`, `sbomVerification`, `immutableRelease`, `publicMiningActivation`, and `publication` present with null values. Any positive canonical activation/publication state is treated as a promotion attempt and therefore requires the complete release identity, platform assets and digests, the established core evidence set, and the dedicated per-platform SBOM gate; a partially positive verification state cannot be represented as a valid inactive policy.

A future reviewed promotion change must bind one exact 40-hex source commit and one versioned `miner-v*` release tag to all three GitHub Release assets. Core evidence remains non-null and reviewable for Windows signing, macOS signing/notarization, provenance, checksums, immutable release state, and explicit public-mining activation. In addition, `sbomVerified` must be true and Windows, macOS, and Linux must each carry a distinct SBOM evidence reference. Each evidence reference remains bound to the exact source commit or release identity and carries an explicit SHA-256 digest. Evidence byte identities must be disjoint from all promoted platform-asset SHA-256 values and from other security-role evidence, so an end-user miner binary or unrelated review artifact cannot also stand in as SBOM evidence.

Provenance verification reads schema-v3 structured evidence from the exact source-commit Git blob, checks its digest against both immutable and working-tree bytes, and requires explicit positive verification with an approved method. Its subjects must exactly match all promoted platform artifacts and their canonical SBOMs. Missing, duplicated, substituted or cross-release subjects fail closed. This check does not create or attest provenance.

Windows, macOS and Linux signing evidence is mandatory. Each schema-v3 record binds the exact promoted artifact and canonical SBOM subject to the source-commit blob and its SHA-256, with explicit positive verification and the platform-specific approved method. Linux requires detached-signature evidence; see `MINER_LINUX_SIGNING_BINDING.md`. The verifier does not sign or notarize binaries or provision credentials.

Checksum verification binds the exact source-commit evidence bytes, promoted artifact/SBOM subjects and explicit positive verification. The dedicated verifier rejects missing, substituted, aliased or cross-release identities. Passing it does not upload assets or grant publication authority.

SBOM promotion evidence is per-platform and fail-closed. For each promoted Windows, macOS and Linux artifact, the only accepted SBOM evidence URL is the same immutable release directory and exact promoted artifact basename with `.sbom.cdx.json` appended, followed by a lowercase 64-hex `#sha256=` binding. The three SBOM references and three SBOM digest identities must be distinct. Cross-platform substitutions, renamed or cross-release SBOMs, digestless evidence, duplicate SBOM byte identities, and SBOM digests that alias either a promoted miner artifact or another core evidence role are rejected. The gate validates evidence identity and release association; it does not synthesize a missing SBOM, publish assets, grant OIDC/write authority, sign binaries, or activate public mining.

Immutable-release evidence is a schema-v3 record at `evidence/immutable-release.json` in the exact source commit. Its digest must match the immutable blob and working-tree bytes, and its release version, ordered artifact/SBOM subjects and explicit verification must match the policy. This proves evidence integrity, not that GitHub settings were changed by the verifier.

Public-mining activation evidence uses a schema-v3 record bound to the exact source-commit blob, its digest, release version and ordered artifact/SBOM subjects, with explicit positive verification. This validates supplied authorization evidence; it does not activate public mining itself.

Evidence semantics are fail-closed and path-bound rather than inferred from arbitrary role-name substrings. Windows signing evidence is limited to canonical `evidence/windows-signing.json` or `evidence/windows-signature.json` paths at the exact source commit; macOS signing/notarization is limited to `evidence/macos-signing.json` or `evidence/macos-notarization.json`; provenance is limited to canonical `evidence/provenance.json` / `evidence/attestation.json` or exact release assets named `provenance.json` / `attestation.json`; checksum evidence is limited to exact release assets `SHA256SUMS` or `checksums.txt`; per-platform SBOM evidence is limited to the exact promoted artifact basename plus `.sbom.cdx.json` in the same immutable release; immutable-release evidence is limited to canonical `evidence/immutable-release.json` at the exact source commit; and public-mining authorization is limited to canonical `evidence/public-mining-activation.json` or `evidence/public-mining-authorization.json`. The rendered GitHub release-tag HTML page is not accepted as immutable-release evidence merely because a `#sha256=` fragment is appended: URL fragments do not cryptographically bind the page bytes.

Website download activation remains a separate reviewed step and must consume only the same immutable GitHub Release assets after this policy and the public-mining launch gates are independently satisfied. No website or release workflow may infer authorization from successful candidate CI alone.

Publication authorization is independently byte-bound. The canonical `publication` role must reference `evidence/publication.json` at the exact 40-hex `sourceCommit`, with a terminal lowercase SHA-256 matching both the immutable Git blob and the checked-out regular non-symlink file. The structured schema-v1 publication record binds the exact release version and ordered Windows/macOS/Linux artifact plus canonical per-platform SBOM subjects, and requires explicit positive verification using an approved bounded method/tool identity. Mutable refs, path aliases, false verification, unknown methods or fields, release/subject drift, digest mismatch, working-tree substitution, symlink substitution, and evidence-byte aliasing fail closed. This verifier does not publish assets or authorize public mining, public testnet, or mainnet.
