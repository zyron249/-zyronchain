# Miner release promotion boundary

ZyronChain miner packaging and miner publication are separate security boundaries. Candidate workflows may build, checksum, attest, and smoke-test self-contained Windows/macOS/Linux artifacts while public mining remains disabled. Candidate availability alone is not authorization to publish or advertise mining as live.

Candidate checksum generation is also fail-closed at the filesystem boundary. The release manifest must recursively hash every regular file in the candidate tree except the root `SHA256SUMS` file itself, in deterministic path order. Directory traversal must not follow or silently omit symlinks, junction/reparse-style objects, FIFOs, sockets, devices, or any other non-regular entry; encountering one aborts manifest generation. npm executable shims that exist as symlinks in the development `node_modules/.bin` tree are deliberately materialized as regular files during miner packaging, but only when their canonical target remains inside the source `node_modules` tree and resolves to a regular file. The runtime materializer must reject any destination that already exists, even if empty, so stale regular files or prior-run state cannot survive into a candidate and become part of its checksum identity. Freshness is enforced again at the creation boundary: the final destination directory is created non-recursively so a path that appears after preflight fails closed rather than being accepted, and the created directory's canonical identity and source-root separation are revalidated before any source entry is copied. The destination parent must already be a real directory; destination-side substitutions are not followed as a way to satisfy freshness. The materializer must also reject a destination that is the canonical source root or lies beneath it, before creating destination material, so packaging cannot recursively copy the runtime tree into itself and exhaust disk or produce non-deterministic checksum coverage. A symlink that escapes the source root or resolves to a non-regular object aborts packaging rather than copying host data into the candidate. The checksum walker itself remains strict and never follows a symlink in the release candidate. This closes checksum coverage over the complete distributable tree but does not replace platform signing, provenance, immutable-release review, or public-mining activation evidence.

`docs/miner-release-promotion.json` is the fail-closed promotion policy. The schema-v2 top-level object must contain exactly the canonical release identity fields, seven activation/publication/verification booleans, `assets`, `assetSha256`, and `evidence`; unknown, typo, or shadow top-level fields are rejected rather than silently ignored. While launch evidence is incomplete it must keep every canonical activation/publication/verification boolean false, exactly the `windows`, `macos`, and `linux` platform asset keys present with null values, and exactly the canonical evidence keys `windowsSigning`, `macosSigningOrNotarization`, `provenance`, `checksums`, `immutableRelease`, and `publicMiningActivation` present with null values. Any positive canonical boolean is treated as a promotion attempt and therefore requires the complete release identity, platform assets and digests, evidence set, and all remaining promotion gates; a partially positive verification state cannot be represented as a valid inactive policy. The promotion verifier rejects unexpected top-level fields, missing/extra platform keys, missing/extra evidence keys, partial activation, partial asset publication, untrusted asset origins, non-exact source identities, mutable-release state, or missing evidence.

A future reviewed promotion change must bind one exact 40-hex source commit and one versioned `miner-v*` release tag to all three GitHub Release assets. All six canonical evidence fields must become non-null reviewable references: Windows signing, macOS signing/notarization, provenance, checksums, immutable release state, and explicit public-mining activation. Each evidence reference must remain bound to the exact source commit or release identity and carry its explicit SHA-256 digest. After the terminal `#sha256=` binding is removed, the six underlying evidence references must be pairwise distinct, and the six SHA-256 byte identities must also be pairwise distinct. Evidence byte identities must additionally be disjoint from all three promoted platform-asset SHA-256 values, so an end-user miner binary cannot also stand in as signing, provenance, checksum, immutable-release, or activation evidence. One review artifact cannot satisfy multiple security roles merely by being repeated at the same URL, copied to a different URL, relabeled with a different digest fragment, or aliased to the bytes of a distributable miner artifact.

Evidence semantics are fail-closed and path-bound rather than inferred from arbitrary role-name substrings. Windows signing evidence is limited to canonical `evidence/windows-signing.json` or `evidence/windows-signature.json` paths at the exact source commit; macOS signing/notarization is limited to `evidence/macos-signing.json` or `evidence/macos-notarization.json`; provenance is limited to canonical `evidence/provenance.json` / `evidence/attestation.json` or exact release assets named `provenance.json` / `attestation.json`; checksum evidence is limited to exact release assets `SHA256SUMS` or `checksums.txt`; immutable-release evidence is limited to canonical `evidence/immutable-release.json` at the exact source commit; and public-mining authorization is limited to canonical `evidence/public-mining-activation.json` or `evidence/public-mining-authorization.json`. The rendered GitHub release-tag HTML page is not accepted as immutable-release evidence merely because a `#sha256=` fragment is appended: URL fragments do not cryptographically bind the page bytes. Misleading filenames that merely contain role keywords are rejected even when their source/tag and SHA-256 bindings are otherwise valid. The verifier does not prove those external facts by itself; it only prevents the repository policy from representing a partial, aliased, role-confused, path-confused, ambiguous, byte-identity-aliased, cross-class-byte-aliased, or incompletely shaped evidence set as authorized.

Website download activation remains a separate reviewed step and must consume only the same immutable GitHub Release assets after this policy and the public-mining launch gates are independently satisfied. No website or release workflow may infer authorization from successful candidate CI alone.
