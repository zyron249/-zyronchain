# P2P checkpoint resource bounds

The native checkpoint protocol is transport for an externally authenticated checkpoint anchor; a peer response is never a trust source.

Checkpoint snapshots are limited to 64 MiB and transferred in bounded chunks. On the serving side, the canonical local snapshot is materialized at most once per finalized tip while retained in the recent-tip cache. Retention is bounded by both entry count and aggregate bytes: at most two snapshots may coexist, and their combined binary footprint may never exceed the same 64 MiB canonical snapshot ceiling. Two small recent snapshots can therefore survive ordinary tip advancement, while a near-limit newer snapshot evicts older cached entries instead of allowing roughly 128 MiB of retained checkpoint buffers. The canonical candidate is cached independently of the requester-supplied digest, so repeated requests with an incorrect digest cannot force repeated full serialization of the same finalized tip. The supplied digest is still required to match before any checkpoint bytes are served.

On the client side, the first authenticated/validated response fixes the bounded `totalBytes` value. The receiver allocates one destination buffer of that exact size and copies each canonical base64-decoded chunk directly into the validated offset. It does not retain a second `Buffer[]` copy of the full transfer and does not call `Buffer.concat` after download completion. Metadata drift, offset mismatch, oversized chunks, incomplete transfers and digest mismatch remain fail-closed.

After download completion the receiver authenticates the exact byte buffer against the externally supplied snapshot SHA-256 before UTF-8 conversion. Before `JSON.parse` can allocate the decoded object graph, the already-bounded bytes are scanned with explicit complexity ceilings: JSON nesting is limited to 64 levels and structural punctuation to 250,000 tokens. Punctuation and escaped quotes inside JSON strings do not count toward those limits. Over-bound checkpoints fail before object-graph allocation.

Once the UTF-8 representation exists, the completed binary buffer reference is released before JSON parsing. After parsing, the original full UTF-8 string reference is also released. Canonical equivalence is then verified with a streaming canonical digest traversal: the parsed value is walked in the same UTF-16 key order and safe-integer/depth/cycle semantics as `canonicalJson()`, while canonical fragments are fed directly into SHA-256 and a UTF-8 byte counter. Checkpoint validation therefore does not build a second normalized object graph and does not materialize one full canonical output string merely to compare the canonical length/digest with the external anchor. Long string values are escaped in bounded chunks, avoiding a second full escaped-string representation at this verification boundary.

Consensus serialization call sites continue to use `canonicalJson()`; the hash-only primitive is used here only for memory-sensitive checkpoint canonical-equivalence verification. Regression coverage requires its byte length and SHA-256 to match `canonicalJson()` across nested arrays/objects, UTF-16 key ordering, escaped/long strings, negative zero, safe integers, array null behavior and object omission behavior.

The parsed snapshot object still remains necessary for trusted finality/governance/State-v2 reconstruction, and that reconstruction can require substantial target-scale memory. These controls reduce transient checkpoint-verification and serving-cache peak memory but do **not** constitute target-hardware capacity evidence and do not close the State-v2 capacity/recovery STOP-SHIP gate tracked by #383.

These controls do not weaken chain/genesis identity checks, the externally supplied tip/digest anchor, finality validation, State-v2 validation, or any public-mining/public-testnet/mainnet activation gate.
