# P2P checkpoint resource bounds

The native checkpoint protocol is transport for an externally authenticated checkpoint anchor; a peer response is never a trust source.

Checkpoint snapshots are limited to 64 MiB and transferred in bounded chunks. On the serving side, the canonical local snapshot is materialized at most once per finalized tip while retained in the recent-tip cache. Retention is bounded by both entry count and aggregate bytes: at most two snapshots may coexist, and their combined binary footprint may never exceed the same 64 MiB canonical snapshot ceiling. Two small recent snapshots can therefore survive ordinary tip advancement, while a near-limit newer snapshot evicts older cached entries instead of allowing roughly 128 MiB of retained checkpoint buffers. The canonical candidate is cached independently of the requester-supplied digest, so repeated requests with an incorrect digest cannot force repeated full serialization of the same finalized tip. The supplied digest is still required to match before any checkpoint bytes are served.

Uncached snapshot creation is also globally single-flight across checkpoint peer connections. Concurrent authenticated requests for the same finalized tip join one in-flight snapshot/canonical serialization rather than multiplying the transient snapshot graph, canonical text and binary-buffer footprint. If finality advances while a different tip is still being materialized, the second tip fails closed instead of starting another large build concurrently; a later retry may materialize the new current tip after the in-flight slot clears. The slot is cleared on both success and failure, so a failed build cannot poison future retries. The completed candidate must still match the originally requested finalized tip before it is admitted to the bounded cache.

On the client side, the first authenticated/validated response fixes the bounded `totalBytes` value. The receiver allocates one destination buffer of that exact size and copies each canonical base64-decoded chunk directly into the validated offset. It does not retain a second `Buffer[]` copy of the full transfer and does not call `Buffer.concat` after download completion. Metadata drift, offset mismatch, oversized chunks, incomplete transfers and digest mismatch remain fail-closed.

Crash-safe portable State-v2 resume/cache files are descriptor-bound before reading and retain their explicit manifest/chunk byte ceilings, regular-file/no-symlink checks, descriptor identity checks, post-read path revalidation and fail-closed concurrent-growth detection. The read buffer is sized to the descriptor-bound file size plus one overflow byte rather than to the caller's entire ceiling. A small resume chunk therefore no longer allocates a 20 MiB-class transient buffer merely because the protocol ceiling permits a chunk that large; the extra byte still detects growth beyond the bound object or configured ceiling without unbounded reading.

The durable `p2p-state-checkpoints` serving cache is additionally bounded to 512 MiB of aggregate real-file content while retaining the existing maximum of two canonical checkpoint directories. Accounting recursively follows only real directories and regular files; canonical checkpoint symlinks, nested symlinks, non-regular entries, missing protected paths, accounting overflow, or directory identity changes fail closed. Active/in-memory checkpoint directories are protected from quota eviction. If protected material alone exceeds either the byte ceiling or two-entry ceiling, serving fails closed rather than deleting in-use data. Completed historical cache admission and newly materialized current-tip admission both run the same pruning boundary, preventing startup-only accounting from being bypassed by later checkpoint reuse or creation.

The dedicated durable cache root is also closed against non-canonical leftovers. Regular files or real directories whose names are not canonical checkpoint identities are treated as stale cache material and removed only after the full root and all protected canonical paths have been validated. Root-level symlinks and other unsafe filesystem objects fail closed and are never followed. Stale artifacts therefore cannot accumulate outside the 512 MiB resource boundary or displace an active protected checkpoint.

After download completion the receiver authenticates the exact byte buffer against the externally supplied snapshot SHA-256 before UTF-8 conversion. Before `JSON.parse` can allocate the decoded object graph, the already-bounded bytes are scanned with explicit complexity ceilings: JSON nesting is limited to 64 levels and structural punctuation to 250,000 tokens. Punctuation and escaped quotes inside JSON strings do not count toward those limits. Over-bound checkpoints fail before object-graph allocation.

Once the UTF-8 representation exists, the completed binary buffer reference is released before JSON parsing. After parsing, the original full UTF-8 string reference is also released. Canonical equivalence is then verified with a streaming canonical digest traversal: the parsed value is walked in the same UTF-16 key order and safe-integer/depth/cycle semantics as `canonicalJson()`, while canonical fragments are fed directly into SHA-256 and a UTF-8 byte counter. Checkpoint validation therefore does not build a second normalized object graph and does not materialize one full canonical output string merely to compare the canonical length/digest with the external anchor. Long string values are escaped in bounded chunks, avoiding a second full escaped-string representation at this verification boundary.

The native State-v2 serving path uses the same streaming canonical digest primitive when authenticating the live finalized snapshot against the externally supplied full-snapshot SHA-256. It therefore preserves the exact existing digest contract without first constructing a normalized clone plus one full canonical JSON string solely for hashing before portable State-v2 materialization. Finalized tip/state-root checks, durable serving caches, Noise/chain identity, chunk bounds, poison/failover behavior, and trusted finality/governance/State-v2 reconstruction remain unchanged.

Consensus serialization call sites continue to use `canonicalJson()`; the hash-only primitive is used only at memory-sensitive checkpoint/State-v2 digest verification boundaries. Regression coverage requires its byte length and SHA-256 to match `canonicalJson()` and guards the State-v2 serving selector against reintroducing `sha256Hex(canonicalJson(snapshot))` at that boundary.

The parsed snapshot object still remains necessary for trusted finality/governance/State-v2 reconstruction, and that reconstruction can require substantial target-scale memory. These controls reduce transient checkpoint-verification and serving peak memory but do **not** constitute target-hardware capacity evidence and do not close the State-v2 capacity/recovery STOP-SHIP gate tracked by #383.

These controls do not weaken chain/genesis identity checks, the externally supplied tip/digest anchor, finality validation, State-v2 validation, or any public-mining/public-testnet/mainnet activation gate.
