# Miner platform-signing evidence boundary

`platformSigningVerified=true` is a release stop-ship assertion, not a value inferred from candidate CI. The miner promotion gate must therefore reject a promotion unless each canonical Windows, macOS, and Linux signing/notarization evidence reference is byte-bound to a regular file in the exact immutable `sourceCommit` Git tree and the checked-out working-tree copy matches those bytes without symlink substitution.

For an active promotion, the terminal `#sha256=` value on each signing evidence URL must equal the SHA-256 of the exact `sourceCommit:path` Git blob. The evidence file uses signing schema version 3 and contains exactly the promoted `releaseVersion`, same-platform artifact name/digest, exact corresponding SBOM name/digest, and a `verification` object. The `sourceCommit` identity is deliberately supplied by the immutable Git URL/object binding rather than duplicated inside the evidence bytes: requiring a file stored in a commit to contain that same commit hash would create an impossible self-referential hash requirement. `verification.verified` must be literal `true`; the method must be platform-approved (`authenticode` for Windows, `codesign` or `notarization` for macOS, `detached-signature` for Linux), and the tool identity must be explicit and bounded.

The verifier resolves evidence through the local Git object database only; it does not fetch evidence from the network. Missing Git objects, metadata-only legacy evidence, false/unknown verification, digest drift, cross-platform substitution, mutable branch references, working-tree drift, missing evidence files, symlinks, and non-regular Git tree entries fail closed.

This repository check validates evidence structure, exact source-blob identity, subject identity, local byte equality, and the declared successful verification result. It does **not** create a signature, notarize an application, provision signing credentials, independently establish signer trust, publish a GitHub Release, or authorize public mining. Real platform/tool-produced signing or notarization evidence remains required and reviewable under issue #390 before any release publication or website download activation.

The inactive canonical promotion policy remains unchanged: all activation/publication verification flags are false, release identity and platform assets are null, and no signing evidence is accepted as authority merely because packaging or release-candidate CI succeeded.
