# Miner runtime source snapshot boundary

Miner release-candidate runtime materialization is fail-closed against in-place regular-file mutation, pathname replacement, symlink traversal at the descriptor-open boundary, destination-path replacement during a file copy, and acknowledged success before candidate bytes and namespace updates reach the local filesystem durability boundary.

For each ordinary regular source file and each canonical in-root npm symlink target, the materializer binds the validated source to a descriptor snapshot containing device/inode identity, byte size, modification time, and change time. On supported POSIX packaging targets the source descriptor is opened with `O_RDONLY|O_NOFOLLOW`; candidate destination files are opened with `O_WRONLY|O_CREAT|O_EXCL|O_NOFOLLOW`. A source pathname replaced by a symlink immediately before `open` therefore fails closed instead of traversing the replacement target. Explicit npm symlinks that were already validated as in-root regular-file targets remain supported by resolving the allowed link first and applying the no-follow open to that canonical target path.

The opened source descriptor must still match the pre-open snapshot before any destination file is created. After all source bytes have been read, the descriptor is revalidated again; an in-place mutation during the copy aborts candidate construction rather than accepting a mixed or post-validation byte stream. Platforms that cannot provide a non-zero `O_NOFOLLOW` capability do not receive a pathname-following fallback from this helper.

Destination custody is bound at completion of each regular-file copy. After the destination descriptor has received the bytes, mode update, and `fsync`, the helper compares the descriptor's regular-file device/inode identity with an `lstat` of the candidate pathname. A pathname that disappeared, became a symlink or other non-regular entry, or was replaced with a different inode causes the materialization to fail closed rather than accepting attacker-selected candidate bytes. This check establishes the identity of the pathname at the helper's completion boundary; later modification of artifacts remains covered by downstream checksum/provenance and immutable-release controls.

Candidate durability is also fail-closed. After all bytes and mode changes for a destination regular file are complete, its descriptor is `fsync`ed before close. Populated destination directories are opened with the same no-follow boundary, identity-checked around the directory `fsync`, and the candidate root plus its containing parent directory are synced before successful materialization returns. An `fsync` error is propagated as a packaging failure; the helper does not silently downgrade to a success path with weaker crash-consistency semantics. This establishes a local filesystem durability boundary only; it does not promise storage-controller, hypervisor, or remote-volume durability beyond the host filesystem's `fsync` contract.

This rule complements, and does not replace, source-root confinement, directory identity checks, destination freshness/atomic creation, strict release-manifest coverage, platform signing/notarization, provenance, immutable-release review, or explicit public-mining activation. Passing this boundary is local release-candidate integrity and crash-consistency evidence only and is not public-mining, public-testnet, or mainnet readiness evidence.
