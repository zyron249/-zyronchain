# ZyronChain permissionless mining

## Status

Permissionless ZYN issuance is implemented by the canonical Layer-1 binary under **protocol version 5**. Protocol v4 remains intentionally unsupported so existing fail-stop upgrade tests and historical compatibility contracts are preserved.

This feature does **not** replace ZyronChain validator finality. Validators continue to propose, attest and finalize blocks. Miners independently perform proof-of-work to earn permissionless issuance claims, and a finalized block may include at most one valid mining claim.

Public-network activation remains evidence-gated. Mining code existing in the binary is not, by itself, an announcement that the public testnet or mainnet is active.

## Supply and issuance

- Maximum historical ZYN issuance: **50,000,000 ZYN**.
- One ZYN: `100,000,000` atoms.
- Initial mining reward: **6.25 ZYN** per successful finalized claim.
- Halving interval: **4,000,000 successful finalized mining claims**.
- At the current 30-second block cadence, a fully occupied four-million-claim era is approximately 3.8 years.
- Genesis allocations reduce the remaining mining budget atom-for-atom.
- A public zero-premine profile can use only zero-value genesis allocations; those entries initialize required addresses without creating circulating ZYN.
- Transaction fees remain burned. Burned ZYN does not reopen mining headroom.

The protocol tracks the number of finalized mining claims in a consensus-owned reserved account:

`ZYN0000000000000000000000000000000000000000`

Its balance remains zero; its account nonce is the global finalized mining-claim counter. It cannot be used as the activity pool or receive a genesis allocation.

## Proof-of-work challenge

Each mining solution is domain-separated and binds all of the following:

- chain ID;
- miner account nonce;
- miner address;
- next block height;
- previous finalized block hash;
- protocol-derived reward amount;
- 64-bit hexadecimal work nonce;
- miner public key.

Consequences:

- work cannot be precomputed before the preceding finalized block is known;
- another wallet cannot steal a solution by replacing the payout address;
- a solution for one chain, height, reward era or miner nonce is invalid in another context;
- a stale solution is rejected after the finalized tip changes.

The initial target is a 20-bit SHA-256 proof-of-work threshold. This target is an issuance anti-spam/competition threshold; it is not the mechanism that selects the block proposer.

## Consensus validation

A mining claim is accepted only when all of these conditions are true:

1. protocol v5 is active at the target height;
2. the claim is a version-2 domain-separated signed transaction;
3. the miner public key derives to the claimed `ZYN...` sender address;
4. the miner account nonce is exactly next;
5. the claim targets the exact next height and current finalized tip hash;
6. its reward exactly matches the deterministic halving/cap schedule;
7. its proof hash meets the configured target;
8. the block does not already contain another mining claim;
9. applying the reward cannot exceed the immutable historical 50M ZYN ceiling.

Authenticated State-v2 commits both the miner account change and the global mining-claim counter, so checkpoint/restart/replay must reproduce the same issuance history.

## Run the standalone miner

Build the canonical L1 first. Use an encrypted wallet generated by the ZyronChain wallet workflow.

```sh
cd l1
npm ci
npm run build
npm run mine -- \
  --genesis /path/to/genesis.json \
  --key /path/to/wallet.json \
  --password-file /path/to/wallet.password \
  --rpc http://127.0.0.1:9137
```

Use `--once` to stop after one accepted claim submission. `--batch-size` controls how many hashes are tried between finalized-tip refreshes.

The miner accepts plaintext HTTP only for loopback RPC. A remote RPC URL must use HTTPS. The miner reads the private key locally, signs locally, and sends only the signed public mining transaction to the node.

## What this model does not claim

This is **hybrid validator-finalized mining**, not Bitcoin-style Nakamoto consensus. Hash power determines eligibility/competition for issuance; it does not directly determine the canonical block chain. A validator proposer can still censor transactions it has received, including mining claims, subject to the broader validator/finality threat model.

If ZyronChain later chooses to make proof-of-work itself determine chain selection, that would be a separate consensus redesign and protocol upgrade, not a cosmetic change to this mining module.
